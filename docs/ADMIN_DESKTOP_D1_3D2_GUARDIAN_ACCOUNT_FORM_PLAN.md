## 1. Current source audit and purpose

The sole target template, `core/templates/core/guardian_account_form.html`, is shared by two administrator workflows and currently uses a raw H1, `form.as_p`, raw non-field errors and an ungrouped submit/Cancel row. Its distinct identity-verification warnings are valuable and **must be preserved**.

- **Create**: GET/POST `core:guardian-account-create` (`guardians/<pk>/account/create/`), view `guardian_account_create`, `mode="create"`, form `GuardianAccountCreateForm`. On successful POST, service generates a new login and temporary password, requires change on first sign-in, records verification/audit, and returns a **one-time, no-store credential slip** rendered by `_credential_slip`. Not a redirect.
- **Link**: GET/POST `core:guardian-account-link` (`guardians/<pk>/account/link/`), view `guardian_account_link`, `mode="link"`, form `GuardianAccountLinkForm`. On successful POST, links an **existing active** login by exact normalized username, records verification/audit and redirects to `guardian-detail` with a success message. **No password is generated or changed**.
- Both views require `@administrator_required("core.add_guardianaccount")`; POST includes CSRF. Each form has **exactly three fields in order**: `username`, `identity_verification_method`, `identity_verification_note`. The link-mode username is labelled "Existing login username" with existing exact-username help; create-mode uses the existing username rules. Verification method choices have exact labels **"In person, with identity documents"**, **"Against existing school records"**, **"Other (described in the note)"**. Verification note is mandatory, **max 200 characters**, currently a **single-line input**, with existing help advising **no document numbers**. Create username form max length **30**, with actual new-login rule **3–30 lowercase characters** (letters, digits, dot, underscore or hyphen, normalized); Link username form max length **150**, to support existing account usernames. Username lookups normalize (NFKC, surrounding whitespace stripped, lower-cased); they are **case-insensitive**, not raw case-sensitive exact comparisons.
- Services `core/guardian_accounts.py` reject existing active account for Guardian, invalid/reused usernames as applicable, inactive existing login, and login already linked to another guardian. They maintain atomicity and `SecurityEvent` records; Guardian accounts and Student data-access grants are **separate**.
- `core/templates/core/guardian_credential_slip.html` and `_credential_slip` are **outside this gate**. The slip has `Cache-Control: no-store, no-cache, must-revalidate, private`; password only passes to that one response. Do not capture, print, commit or log even synthetic credential-slip screenshots in this UI gate.

## 2. Proposed single-gate scope and exclusions

**Approved scope for implementation in a fresh branch after this decision freeze:** one modified template `core/templates/core/guardian_account_form.html`; focused presentation/regression tests; synthetic **pre-submit/invalid** screenshots in `docs/ui-reviews/ui-d1-3d2/`; plan status/doc closeout; at most a tiny, scoped CSS addition in `static/css/erp.css` if unavoidable. Reuse `erp-guardian-form-page` from D1-3D1 and existing `erp-*` tokens, without changing shared partials. Do **not** use `.erp-note` for the static security warning: it belongs to attendance and can be hidden via existing `:has()` behavior. Use the existing Bootstrap 5 `alert alert-warning` (always visible) for security verification above the form. Do not add inline `<style>` blocks; new CSS should be unnecessary. If a narrowly scoped CSS exception is truly needed, **every new selector must begin with `.erp-guardian-form-page`**, including inside media rules, to satisfy the existing D1-3D1 end-of-file CSS regression test.

**No changes to:** `core/views.py`, `core/forms.py`, `core/guardian_accounts.py`, accounts, models, migrations, query scopes, audit, URLs, permissions, templates/base shell, Student/Teacher/Guardian portals, credential-slip template or response headers, shared `_form_field.html` or `_page_header.html`, lockouts, password reset, revoke/username operations, D1-4, Academic Year Rollover. No Tabler runtime and no new JS requirement.

## 3. Proposed design contract

1. Use shared `partials/_page_header.html` with one H1, mode-accurate titles: **Create portal account** / **Link an existing login**; eyebrow "People". Show Guardian's name as escaped readable context in the header purpose, for example "Guardian: {{ guardian.full_name }}" (Django auto-escaping preserved); wrap very long names and unbroken identifiers at 390px (and 360px where feasible). The shared header's `purpose` argument is brief context only, **not** a replacement for the security warning. Never hard-code real account usernames or secrets.
2. Immediately **above the form**, render a persistent, non-dismissable `<div class="alert alert-warning">` containing this **exact common text** (including on invalid POST): **"Identity verification required. Confirm that you have already verified this person's identity as the Guardian shown above. Select the method actually used and record a brief note. Do not enter document numbers. The system records your verification; it does not verify identity automatically."** The bolded leading phrase may be `<strong>`; do not render it as a JS or auto-dismissing toast, or as an assertive live-region alert on initial page load. Keep the existing field-level no-document-numbers helper. Do not add ID-number, document upload or evidence fields.
3. For **Create**, show this **exact mode-specific instruction** above the form, separately from the common warning: **"Creating this account generates a temporary password shown only once on the next page for offline delivery. The Guardian must change it at first sign-in. Creating an account does not automatically grant access to any Student."** Keep one-time slip generation/no-store unchanged.
4. For **Link**, show this **exact mode-specific instruction** above the form, separately from the common warning: **"Enter the existing login's username. Matching is case-insensitive after normalization; it does not search by name, phone or email. The existing password will not change. Linking this login does not automatically grant access to any Student."** A teacher who is also a parent is an existing legitimate example. **Never** add username search/suggestions, account-existence previews, autofill from student/phone/email/name, or password inputs in this visual gate. Do not modify `forms.py` to add `autocomplete="off"` and do not use template JS to defeat browser/password-manager autofill; keep existing behavior and record the risk.
5. Use `<form method="post" class="erp-form">`, unchanged same-URL POST target, `{% csrf_token %}`, `partials/_form_required_legend.html`, `form.non_field_errors` **once** inside `erp-form-errors` with `role="alert"` when present, and iterate unchanged `form` fields through `partials/_form_field.html` in the supplied order. Maintain submitted values and field errors on invalid POST. No shared component refactor.
6. Use `erp-form-actions` for exact existing labels **Create account** / **Link login**, and a Cancel GET link to `core:guardian-detail` with the same `guardian.pk`. No destructive styling for standard actions and no additional irreversible confirmation step. Keep one submit button and one Cancel link; do not accidentally submit on Cancel.
7. Preserve view-/service-enforced outcomes and authorization. Link creates a link only: no password change or Student access grant. Create goes to the unchanged one-time slip; link redirects to Guardian detail. Errors are shown, not swallowed. Do not display a temporary password before a successful Create POST or anywhere on Link pages.
8. Do not replace the server form with JavaScript, client-side identity checks, live username existence tests or new browser storage. Native validation and keyboard usage remain usable with JavaScript off.

## 5. Known issues explicitly deferred

- **Permission asymmetry:** A user may have `core.add_guardianaccount` and submit Create/Link but lack `core.view_guardian`, so Cancel or Link success destination may 403. Do not silently broaden roles or change destination in a template-only gate; document a separate workflow/permissions decision.
- **Shared form-field ARIA associations** (`aria-invalid` / `aria-describedby`) are not guaranteed by `_form_field.html`. Separate shared-component accessibility review only.
- **Guardian credential slips, reset and revoke screens** remain outside scope. Their sensitive response behavior is protected by regression checks, not UI migration here. The visually older credential slip may be assessed for a possible **D1-3D3**, after a separate security/print specification and explicit authorization.
- **Sidebar keyboard focus styling** and desktop Cancel height are global/shared UI follow-ups, not reasons to widen this gate.
