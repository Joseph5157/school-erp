## 1. Objective and source audit

Make the **administrator** Attendance Register Detail and Correction pages coherent, accessible and responsive while keeping the exact Draft/Submitted/correction workflows, permissions, data and POST semantics. No new attendance feature, grade calculation, student report or teacher/guardian UI.

Two template targets:

1. `core/templates/core/attendance_register_detail.html` — currently a raw `<h1>`, metadata `<dl>`, one Draft roster or Submitted table. Draft form uses `core/_attendance_capture_table.html` shared with Teacher Attendance; the Submitted table is not in a labelled `erp-panel` / `erp-table-scroll`. The current `marked_count` is the **count of saved entries**, not a count of all enrolled students.
2. `core/templates/core/attendance_correction_form.html` — already uses the shared `_page_header.html`, `erp-form`, required legend, `_form_field.html`, errors and actions. Improve only metadata/status readability and the **Correction history** table composition/semantics; do not rewrite this working form.

Current view and domain contracts (read at `288fc0d`):
- `attendance_register_detail` GET requires **`core.view_attendanceregister`** and supplies exactly `register`, `entries`, `capture_form`, `marked_count`.
- **Draft** (`not register.is_submitted`): header/metadata + enrolled roster size `capture_form.enrollments|length`, saved `marked_count`, explicit **unmarked != Absent** guidance. If roster exists and `core.add_attendanceentry` is granted, show existing `<form method="post" action="{% url 'core:attendance-capture' register.pk %}" id="attendance-capture">` with CSRF and `{% include "core/_attendance_capture_table.html" with can_submit=perms.core.change_attendanceregister %}`. Without capture permission show original denial text, **not** an editable roster. If no enrollments show original empty-roster message and **no capture form**.
- Shared capture partial exposes exactly **Save draft** (`name="action" value="save"`) and, only for `core.change_attendanceregister`, **Save and submit** (`name="action" value="submit"`). Each row's Present/Absent status may remain **unmarked** in a Draft; note is valid only for Absent. Submission requires a complete, instructional, date-effective roster, valid actor and calendar/day; server actions remain unchanged. The Teacher Portal uses this SAME partial with HTMX autosave; it is **not** editable in D1-4B.
- **Submitted** (`register.is_submitted`): show submitted time/by, read-only rows from `entries` in **the existing queryset/model order**, and per-row **Correct** link only with **`core.change_attendanceentry`**; absent this permission, do not render the action column. Student name currently links to `core:student-detail`; preserve existing links even when the viewing account lacks separate Student-detail rights (record cross-permission 403 separately, no silent authorization change).
- `attendance_entry_correct` requires **`core.change_attendanceentry`**; if the register is Draft, it redirects to the register detail with an informational message. On a Submitted register it renders `AttendanceCorrectionForm`, with **`status`**, **`absence_note`**, **`reason`**, in their existing field order. Reason is mandatory; a note is optional only if correcting to Absent. On a successful change the service appends an immutable correction, updates the accepted entry and redirects to register detail. No-op, invalid status, missing reason, or Present with a note must remain rejected. Changing to Present clears the note. The history query `entry.corrections.select_related("corrected_by")` retains the model's **newest-first** ordering.
- The history's **six current columns** are When, From, To, Note change, Reason, By. It displays previous vs new status and note exactly, only renders note-change text when values differ, and has a truthful empty case. Do not change event timestamps, author, reason or comparison logic.

## 3. Register Detail — target layout contract

1. **Header and back navigation:** use `partials/_page_header.html` with **one H1** (e.g. "Attendance register"), eyebrow "Attendance", and a short context line containing **existing** Section and register date. Show a `_status_badge.html`-style readable **Draft** / **Submitted** state, using *the actual* `register.status` (`status_label=register.get_status_display`; `status_tone=register.status|lower` if supported by the existing include; alternatively a single status badge in metadata). Keep long hyphenated and unbroken Section/Academic Year names visible and escaped. A simple **Back to attendance** GET link to `core:attendance-register-list` is optional; it must not promise preservation of query state not present in detail URLs. Browser Back retains previous filters; do not use unsafe Referer forwarding.
2. **Context panel:** present the existing **Academic year, Class/Grade, Section, Date (weekday), Register status**, and for Submitted **Submitted at/by** in a readable description list / compact `erp-panel`. Do not add inferred counts, extra audit fields, percent-complete or publication claims. The Draft helper remains truthful: **"Attendance started, not yet official."**
3. **Draft view:** keep heading **Roster**, existing precise `capture_form.enrollments|length` and `marked_count`, and the statement **"Unmarked Students are not treated as absent."** Prefer small context/status copy above the form. Wrap only around (not within) the unchanged capture include. **Do not** add a second submit button, fake progress control, implicit "mark all absent", modal, auto-submit or form nesting. Preserve the original `id="attendance-capture"`, exact action URL, `method="post"`, CSRF, `Save draft` and conditional `Save and submit`.
4. **No capture rights:** keep the permission branch and text; do not show actionable rows or form controls. The view's GET still works for accounts with `view_attendanceregister`. Do not imply that a user with `change_attendanceregister` alone can capture without `add_attendanceentry`.
5. **Empty roster:** when no date-effective enrollments, show a clear neutral empty state **"No Students are enrolled in this Section on this date."** No submission action and no absent count. Do not fabricate an unrecorded-student list.
6. **Submitted view:** heading **Submitted attendance** and a proper `erp-panel` with a labelled, keyboard-focusable `erp-table-scroll` (`role="region" aria-label="Submitted attendance" tabindex="0"`). Retain columns **Student, Status, Absence note** and **Actions** only for the current `change_attendanceentry` permission; exact Student links, **Correct** target and row order. Use `<th scope="col">`, appropriately labelled Actions header, status text **Present/Absent** (color may supplement text, not replace it), blank note meaning no note (not missing attendance). Correct remains a link, not a submit button. Preserve a truthful empty case and set `colspan` according to rendered columns (3 vs 4). No Draft roster form on a Submitted page.
7. **Meaning:** Submitted badge means only that the register was officially submitted, not that everyone is Present. Rows show accepted status including corrections. Do not reinterpret saved Draft entries as reportable attendance or calculate attendance percentages on this page.

## 4. Correction Form + History — target layout contract

1. Keep one H1 `Correct attendance` and existing page-header eyebrow/purpose (already standardized). Context grouping may use `erp-panel` or a compact description list; preserve **Student, Section, Date, Current status** and optional current Absence note. The name is autoescaped and wraps. Show current status as text or shared badge without introducing extra states.
2. Preserve the existing explanatory line when an absence note is present: **"Correcting this entry to Present clears its absence note."** Do not suggest that a no-op correction is allowed.
3. Keep the existing `erp-form` as-is: `POST` same URL, CSRF, `_form_required_legend.html`, form-level errors once when present, each field in original order via `_form_field.html`, exact submit **Save correction** and GET **Cancel** to `core:attendance-register-detail` for that register. Do not add a second reason field, client-side status logic, confirmation modal, or new validation.
4. Keep heading **Correction history**. Wrap existing history table in a separate `erp-panel` and retain its **labelled keyboard-scrollable region** exactly. Add a real table `<caption class="visually-hidden">` and `scope="col"` for six headers; no seventh field or export action. **When / From / To / Note change / Reason / By** must show same source values and **newest-first order** from the unchanged queryset. Keep note-change text only when notes differ and show `(none)` for a missing old/new note only in that diff; no row truncation or misleading ellipsis. Show the existing no-corrections message truthfully. No new history count unless provided by existing data without query growth.
5. Responsive correction history: long reasons, notes and actor names should remain readable. Table-local horizontal scrolling is acceptable for a six-column audit log; no document-level overflow. All correction history remains readable through keyboard scrolling, including at 200% zoom.

## 7. Deferred scope / risks logged separately

- **D1-4C:** admin Attendance Reports index and daily absentees, missing attendance, monthly Section and Student history pages.
- The shared `core/_attendance_capture_table.html` plus its JS/HTMX integration and Teacher Portal layout are **not** redesigned. Any shared roster refactor needs its own cross-portal review.
- Limited users may have `view_attendanceregister` but lack `view_student`; existing submitted-row Student-detail links can lead to 403. No silent link removal/permission expansion in this template gate.
- Attendance correction form is reachable with `change_attendanceentry` independently of the register detail's `view_attendanceregister`; existing successful redirect can therefore 403 under asymmetric permissions. Separate workflow permission decision.
- The existing row date/order and correction history order must remain as returned; no sorting, pagination, loading changes or implied "newest" outside the actual correction model ordering.
- Global shared shell 200%-zoom edge cases, shared form-field ARIA, Student/Teacher/Guardian portals, PDF issue/report calculations and academic-year calendar rule changes are separate future work.

**Checkpoint:** This document is the D1-4B implementation contract only. Implementation may proceed on a new dedicated branch via a narrowly scoped Claude Code prompt. Design acceptance, merge and deployment are **separate** decisions.
